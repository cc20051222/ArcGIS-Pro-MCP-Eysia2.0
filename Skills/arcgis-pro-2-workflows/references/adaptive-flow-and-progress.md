# 场景适配、流程展示与过程成果

适用于制作、多步骤、长耗时或用户明确要求观看过程的任务。目标是选择**当前约束下合适且可解释的流程**，持续呈现真实变化；不宣称数学全局最优。普通查询不强制建图、写任务记录或套完整审批。

所有制作流程按 [质量、复检与最终验收](quality-and-acceptance.md) 增加适用的质量要求和检查步骤。业务场景与行业覆盖项组合选择；资料预检、过程/首次检查、复检、最终交付检查和外部验收分开展示，不能把工具完成当成验收完成。

## 1. 先组合现场条件，再选步骤

| 现场条件 | 影响的选择 | 不充分时怎么做 |
|---|---|---|
| 业务目标与成果用途 | 距离缓冲/路网可达、总量/率、分析/制图、正式/草图 | 问会改变结果含义的缺口，避免让用户选择工具名 |
| 数据身份与范围 | 原件/副本、地图/数据集、全量/选择/查询、时相 | 先只读检查；同名歧义不默选 |
| 科学条件 | CRS/单位、栅格格网/NoData、权重/样本、网络模式 | 必要条件缺失则阻断依赖项，不用低质量替代充数 |
| 实际能力 | 当前 schema、真实实现、宿主、许可、可访问源 | 注册名或配方命中不能证明可执行 |
| 工程状态与授权 | 未保存编辑、活动视图、保护对象、具体写入范围 | 保留用户现场，不自动保存、激活地图或关闭只读 |
| 成本与输出 | 数据规模、工作区、格式、页幅、分辨率、预览频度 | 用相关历史实测作参考，避免全表拉取/重复导出；无样本不造工时 |

在满足方法正确、授权、保护和成果标准后，优先更少重复 IO、较少调用、可检查和可恢复的方案。只有在这些硬条件相同的候选间比较便利和速度。用户指定有效方法时保留其选择；存在业务等价的选项可解释推荐理由，不必把每个技术选项都交用户决策。

`suggest_workflow` 当前是冻结六场景的关键词匹配；`matchScore` 不是完成概率，`costEstimate.toolCalls` 不是耗时，所需输入只按键判断。可以用作候选索引，不把它当现场优化器或许可/科学验证器。`get_performance_stats` 有相关历史记录时可辅助估计区间，并说明数据量、宿主和样本差异；无可比样本写“耗时未估计”。

## 2. 场景如何生成合适流程

| 场景 | 常用骨架，可按实际删减或组合 | 必须分叉的条件 |
|---|---|---|
| 快速查询/定位 | 发现对象→只读查询→答复 | 歧义才提问，通常不需要预览和任务板 |
| 数据整理与质检 | 清单→画像/规则检查→问题报告→获准后副本修复→同口径复检 | 仅检查则止于报告；原件修复另核范围 |
| 矢量分析与统计 | 身份/范围/CRS→方法与新输出→执行→数量/空间/统计核验 | 网络与几何距离分开；全量与选择分开 |
| 栅格/多期遥感 | 时相/波段/格网→必要预处理→算法→NoData/对齐/内容核验→预览 | 分类/连续重采样不同，不可比影像先解决条件 |
| 网络/空间统计/情景 | 数据与许可→方法前提→计算→假设/分母/敏感性检查→解释 | 缺网络、样本不足、缺参照时停止相应结论 |
| 专题图与地图册 | 数据语义→符号与规格→拥有布局→试页预览→正式导出→视觉/页序核验 | 不改科学事实；页多先试页，正式 DPI 单列 |
| 文件夹批量任务 | 有界扫描→分型→每类方法→dry run→逐项执行/核验→整批报告 | 截断要披露；不能把一份固定参数用于所有异构目标 |
| GIS→PS | GIS 与事实核验→素材包→核现役 PS 能力→可执行成员→真实保存读回 | 当前源码 PS 业务拒绝执行，整体不宣称已完成 |

跨场景任务按依赖组合，例如“分析并出图”接上统计、布局和交付，不重新检查未变化的所有输入。为步骤保留稳定 ID、依赖、方法、预期产物和验收条件；并行只用于确认不会争用现场的独立读取，工程/编辑/布局/同一输出写入串行。

聊天中的流程图是展示合同，不是后端执行代码。`validate_plan` 只检查其支持的结构；`apply_processing_plan` 不是通用 DAG 引擎：按 targets 和 steps 展开，子调用补入 `target`，**不保证替换工具的 input/output 参数**。先验证逐目标输入绑定、唯一输出和依赖语义；做不到则由 Agent 明确逐项调用受控工具，不能把 Mermaid 或模板变量直接送进去。

## 3. 执行前让用户看懂

展示一张短流程卡：目标、对象与范围、方法及一两句依据、步骤/依赖、精确输出位置、真实缺口。只展示决策摘要和可检查依据，不显示内部推理。客户端支持 Mermaid 才附流程图；文字表始终可用。图中的方法/工具必须由实际 schema 支持，不能直接执行未确认的示例。

下面仅是**展示示意，未执行 GIS**：

| 步骤 | 将做什么 | 验收点 | 状态 |
|---|---|---|---|
| S1 | 识别学校和人口数据，检查范围与 CRS | 对象唯一、单位与统计口径明确 | 待检查 |
| S2 | 按已确认的距离方法生成范围 | 方法、距离、空间范围正确 | 等待 S1 |
| S3 | 按已确认口径统计覆盖人口 | 重叠处理/人口分配与分母明确 | 等待 S2 |
| S4 | 生成 A3 布局并预览 | 图例/指北针/比例尺、中文正常 | 等待 S3 |
| S5 | 正式导出并核验交付 | 实际文件与规格一致 | 等待 S4 |

首次展示不强制再问“是否执行整单”。已有具体授权且前置条件满足就继续；必要授权缺口集中提出。预期产物只显示为计划，实际创建前不加可领取标记。

## 4. 真正可实现的三层“实时”

1. **聊天中的阶段更新，默认使用。** 执行前直接发流程图与状态表，开始、关键结果返回、复检、方案变化或阻断时直接发更新后的状态表。真实图像用用户可见消息内联展示，不只交给工具查看器或写入文件。客户端没有可编辑任务板时追加当前状态，不能假装已经修改旧消息。用户反馈没有看到，说明交付渠道尚未满足展示要求，即使本地文件完整也不能判通过。
2. **现有作业查询，按能力使用。** 取得真实 jobId 后通过 `get_job_status` / `get_job_report` 只读查询；每次返回带观测时间和该 jobId。`done` 是执行成功项，不是质量已核验项；查询本身不推进分片。对于需同 jobId 续跑的任务，先读回、核当前授权/身份/取消意图，再明确执行下一片。
3. **协议推送，仅在客户端与服务器均实证支持时使用。** MCP 的 progressToken/notifications/progress 是可选机制。0.5.0 对应的新产品构件已接入请求级 SSE 和真实事件源；是否已在现役运行须看初始化 experimental 中 arcgispro-mcp/progress 及实际响应，旧插件未更新则不能依赖。它属于协议元数据，不给 GIS 工具凭空增加 `progressToken` 参数。元数据放在协议 params._meta 中，不能塞进工具 arguments。产品构件负责观测和传输，Skill 不新增监听端口，也不自动安装或写客户端配置。

默认按事件更新，能够响应的长任务约 30–60 秒给一次有意义状态；不能保证单次阻塞调用期间采样或发消息。可安全查询且客户端允许并发只读时，可从约 5–10 秒开始、无变化退避至 30–60 秒；总观测预算按用户任务/客户端时限明确限定，超时则标未知并停止轮询，不能认作后台已停止。发生终态、用户停止或连接失效后停止无意义查询；无变化不刷屏。

单次同步工具没有 jobId、进度事件或并发查询能力时，执行前显示“正在执行 X；等待工具返回，内部进度未知”，返回后立即更新。不将估时、动画、调用次数或时间流逝换成真实百分比。不以 `currentShard/shardCount` 或成功步骤占比推断墙钟进度。

### 用户明确要求观看流程时的最低交付

- **执行前**：在聊天直接展示全链路和各步待执行/受阻状态。不要把这一步藏在参考文件或工具输出中。
- **执行中**：关键节点保留“已核验／当前调用／下一步／受阻项”的紧凑表；等待同步调用返回时明确内部进度未知。节点不足 60 秒也要在关键业务事件后更新，不能只按定时发无内容消息。
- **产生预览后**：直接发真实图片并标明阶段与版本。结果链接可同时提供，但不能代替用户要求的内联预览；无图片则写无预览。
- **结束时**：对照原流程显示复检、最终检查和外部验收状态，再交付文件归档。归档是过程的记录，不能补算成先前已完成实时观看。

例如，先发“读取资料：执行中；分析：待执行；首检：待执行；复检：待执行”，读回后直接更新“读取资料：已核验；分析：执行中”。这些状态必须对应当前真实事件；不重放旧记录制造“正在制作”的观感，不为演示而重跑已经完成的 GIS 写入。仅展示补丁规则或旧成果时标为本轮展示整改/历史成果。

## 5. 状态、计数和新版本

聊天使用用户能懂的文字；可选记录采用以下状态：

| 状态 | 含义 |
|---|---|
| PLANNED | 尚未执行，先决步骤或条件未完成 |
| RUNNING | 调用已发出/后端有对应正在执行的证据，内部进度可能未知 |
| PRODUCED | 后端报告该步成功，仍待相关数据/文件/视觉核验 |
| VERIFIED | 有明确检查依据支持本步验收条件 |
| WAITING_USER / BLOCKED | 需要用户具体信息/授权，或依赖能力与数据缺失 |
| FAILED | 有具体失败响应，效果范围仍需按响应核查 |
| CANCEL_REQUESTED / CANCELLED | 已请求取消 / 已确认停止，彼此不可混同 |
| UNKNOWN | 响应丢失、状态无法读回或效果不明 |
| SKIPPED / STALE | 未执行且保留原因 / 目标、输入或方案变化使旧结果不能沿用 |

计数分开显示：“后端成功 9/10、失败 1、待处理 0”和“成果已核验 7/10”。跳过/取消不算成功；没有完整总数就列已知项，不能缩小分母来显示完成。一个作业的计数不能当整个业务流程的完成率，所有工具返回后仍保留核验步骤。

状态板标明计划版本及最近**实际观测时间**，不要用刷新页面时间掩盖旧数据。输入/目标/schema/环境变化生成下一计划版本，说明改了什么、为什么、哪些步骤/成果失效，保留已完成历史；不把旧成果静默贴到新计划。新的输出范围、覆盖、外传或科学方法变化另核授权，格式调整等仍在已授权范围的修改可直接处理。

## 6. 用户边看流程边看成果

- 首次、分析关键节点、试页、正式交付是常用预览点；用户可选简洁/详细或减少预览。批量任务优先代表样本和异常成员，不为每条记录生成图片。
- 地图视图可在当前能力支持时使用 `export_map_view` 返回原生 MCP image content，优先展示返回图像。它需要正确的**当前活动视图**；不匹配时不能自动切换用户地图。默认 96 DPI、长边上限 1200 px、PNG 上限 1 MB 的会话预览不是正式印刷图。
- `export_map_view` 即使省略 outputPath，也使用受控 D 盘中转；核 `usedTransientFile` / `transientFileDeleted`，不宣称物理零写入。不为预览自动改环境配置。其持久 outputPath 会复制覆盖，**默认省略**；确需保存只能在已授权 D 盘自有目录使用确认不冲突的新路径，不为刷新覆盖旧图。
- 布局须展示真实布局导出或相应渲染，地图视图截图不能证明图例、标题和纸面排版合格。预览与最终 `resolution`、页幅及格式分别检查；重预览不改变 GIS 数值、分类阈值或用户布局。
- 数据输出展示总数、已读/样本数、必要字段和小量样例；敏感字段脱敏。大 GDB/PSD 不强行转成图片；提供实际已有文件/目录链接和数据集身份，尚未生成的路径标“计划输出”。
- 图像注明阶段、版本、来源地图/布局、时相、预览/正式和视觉是否核验；内联用真实返回图像或已存在的本地文件绝对路径。图像不支持时给可打开链接和文字结果，不造缩略图、占位结果或假实时画面。
- 图表与状态同时使用文字标签，不只靠颜色；不抢焦点、不反复弹确认。借鉴 W3C 状态消息的易理解与少打断原则，不宣称目标聊天客户端通过 WCAG 认证。

## 7. 可选记录与离线格式化

`assets/task-record.json` 当前 schemaVersion 1.2 包含 `plan`（revision/steps/changes）、`observations`、`presentation` 和 `quality`，简单查询仍不用创建记录。一次 observation 至少有 id、source、observedAt、summary；引用它只表示记录提供了依据，Skill 仍需核实际响应和成果。外部验收在 quality.acceptance 单列；若图中也有外部验收节点，标 required=false，避免把尚待外部裁定混入制作端必须完成的步骤。

每步记录 id、title、dependsOn、state、evidenceRefs、summary；PRODUCED / VERIFIED / FAILED / CANCELLED 要有对应观测引用。产物记录 label、stepId、state（PLANNED/PRODUCED/VERIFIED/STALE）、path，可加 isPreview；PRODUCED / VERIFIED 还须有 observationRef 指向实际观测。未产生或失效者不作为有效下载项。持久预览按授权版本保留，不自动删历史。

`scripts/render_task_board.py` 只读已有 JSON，检查记录结构、步骤 ID/依赖环、观测引用、计数以及展示路径，输出 Mermaid、文字状态表、质量阶段、判据与检查覆盖、未关闭问题、观测摘要、下一步和产物路径到 stdout。质量通过从实际记录的必需项派生，不信任传入的全部通过标记。它不调用 GIS、不验证源事实、不鉴定验收身份、不推送消息、不后台监听。Agent 在真实事件发生后更新记录并重新格式化，再把文本/图像通过客户端实际支持的消息渠道展示。没有 Python 时照相同规范直接发聊天卡即可。

页面/聊天真流式界面属于宿主能力。0.4.1 只有 Skill 指令和离线格式化工具；0.5.0 对应的源码新增 Windows 面板、请求级 SSE 与 GP 回调，但未安装新构件的现役宿主仍没有这些新增实现。聊天直接发送状态卡可以在本轮实际演示；用户是否看见、不同客户端是否渲染、整个 GIS 制作周期能否持续显示须分别检查。不得把静态文件、模拟板或结束后的归档描述为真实作业正在运行。

## 8. 新构件的持续观测与统一展示

新 Add-in 的 MCP 页签提供“任务面板”，本地窗口每 500 毫秒刷新当前进程的有界事件快照，无需额外服务或网络端口。独立面板可以只读 D 盘进度 JSONL；需要在启动宿主前明确配置 ARCGIS_PRO_MCP_PROGRESS_DIRECTORY。业务任务记录通过 ARCGIS_PRO_MCP_PROGRESS_TASK_RECORD 或独立窗口的 --task-record 指定，面板与聊天卡应读同一份记录，避免两套状态。文件变更后自动更新，但后台事件不自动把质量或验收改成通过。

真实事件分三层：所有正常 MCP 工具调用的接收/执行/返回；受控 GP 的 OnBeginExecute、OnProgressMessage、OnProgressPos、OnEndExecute；文件夹作业的实际逐项计数。GP 百分比仅适用于当前 GP 阶段；多次 GP、整体业务完成率和成果核验率不能混算。不发百分比的工具继续显示未知，不让假动画当作工作进度。

支持协议流的客户端以正常 tools/call 请求携带 params._meta.progressToken，同时接受 text/event-stream；通知的 progressToken 必须对应本请求。通知 progress 是单调增加的“观测事件数”，没有人为 total；实际阶段 Completed/Total 在通知元数据 execution 中，不能把事件数当百分比。最终 JSON-RPC 响应结束流，迟到回调不再发送。10 秒 SSE 注释保活仅表示连接仍在，不算内部进展。保留既有协议版本与普通 JSON 路径，不宣称已实现最新版 MCP 的所有传输特性。

面板显示事件时间和无新事件提示；暂停/关闭面板仅停止观看，不取消 GIS。断连、超时或记录不可读不重新派发写工具，实际效果待核查。并发按 invocationId 隔离；网络进度可在拥塞时合并，面板与日志不是无限审计数据库。

此构件已编译、协议夹具和面板窗口可测试；ArcGIS 实机 GP 回调须在获准启用新 Add-in 后另验收。开发文件校验夹具、静态任务记录和历史成图必须明确标注来源，不能冒称正在执行真实 GIS。聊天消息仍由 Agent 在关键节点直接发送；后台窗口不会自行修改旧聊天消息。

## 9. 0.6.0：以完整业务流程为主的实时任务面板

Agent先综合业务目标、真实数据、上下游依赖、当前工具/许可、输出规格与适用条款，再生成整份计划。不能把用户举例当固定算法顺序，不能把开发验收S1/S2当用户业务任务。完整处理、条件步骤及原因、首检、修复、复检、最终检查与外部验收全部先列出；方法、参数/阈值依据、输入/计划输出、检查着重点逐步可展开。水文计划见水文参考，矢量/栅格/制图等仍按对应专业参考适配，不硬编码成水文界面。

继续使用schemaVersion1.2原始记录，新增可选展示字段：每步kind（PREFLIGHT/PROCESS/CHECK/REPAIR/RECHECK/FINAL/ACCEPTANCE）、method字符串、inputs/outputs/checkFocus字符串数组、requirementIds、requestIds。requestIds必须是实际JSON-RPC请求ID的精确字符串，任务间不复用；同一ID只能属于一步，不按工具名猜步骤。quality.requirements包含title/criterion/source/subjectIds/phases/coverageRequired；quality.checks记录实际检查结果和scope。只写“通过”而无方法、证据、覆盖和当前版本不能形成通过状态。

发布前运行 `scripts/publish_workflow.py <本次原始任务记录.json> --target <已配置的面板任务记录.json>`。输入、目标均在已授权D根；目标是Pro启动时ARCGIS_PRO_MCP_PROGRESS_TASK_RECORD配置的实际文件，或独立窗口--task-record所指文件，不靠猜路径。任务切换须 `--activate --expected-task <当前taskId>`；旧开发快照无taskId时用LEGACY。工具不会启GIS/服务或执行修复，仅复用现有校验器派生视图、D盘原子发布并保留内容寻址历史；锁存在时停下对账，不擅删未知锁。

每次开始先记录真实派发观测、将对应步RUNNING并绑定requestId，再发正常MCP；返回时存真实响应/观察并发布PRODUCED或FAILED，业务检查后有新依据才VERIFIED。需要等待用户或能力缺失时标WAITING_USER/BLOCKED，不把估时动画当运行。步骤开始前依赖应已核验；确需改变流程时先记录重规划，不能悄悄越过依赖。新SDK事件可即时覆盖旧步骤执行态，但工具成功最多PRODUCED，不能自动通过质量或验收。

发现缺陷立即保留失败检查，并在quality.issues中记录description/severity/status=OPEN及repair对象：state（REPAIRING/RECHECKING等）、action、affectedStepIds、recheckResult。修复与复检各列步骤并关联当前请求；改数据/参数后更新subjectVersions/plan.revision，旧下游与旧检查标STALE。替换已经完成的检查时将旧check原件放quality.history（可用{"check":旧check}），保留原观测，发布器拒绝抹掉失败。修复动作仍走现有工具与原授权，不为显示自动扩大写入范围。

复检实际重新测量，成功的新RECHECK证据要与首次检查分离；只有问题闭环且所有必需检查有效才提交候选，外部验收另有独立依据。面板“检查与修复”页展示未解决问题、正在处置、受影响步骤、新复检结果及历史检查；完整流程中亦显示各步关联检查。默认首屏为业务总览和步骤详情，内部SDK/请求流在辅助页，用户不必读工具名理解任务。

刷新周期500ms仅表示读取频率；Agent不发布新检查结果时面板保留最近观测并提示无新记录，不能声称检查一直实时更新。SDK只反映已显式绑定的请求；无SDK回调则显示等待/未知。任务记录损坏、过大或暂不可读时清除现役绿色状态并提示，不把上一任务假装成当前结果。聊天仍在业务关键节点直接更新，后台面板不改旧聊天气泡。

## 10. 0.7.0：需求资料确认、工具替代和双显示合同

新任务使用模板 intake 对象。requirements、inputs、outputRoot 都含 status（MISSING/PROVIDED/CONFIRMED）、value、evidenceRefs；输入 value 为路径数组，需求与成果根为字符串。CONFIRMED 要引用真实用户消息的观测；用户已经明确的内容不重复索取，先复述。输出根须绝对 D 路径、实际可写探针，成果和每步计划输出均须位于此根内。输入允许只读 C 路径，不能借此写 C。

dataNeeds 每项记录 id、label、required、reason、recommendation、stepIds、state、evidenceRefs。state 为 MISSING/PROVIDED/VERIFIED/NOT_REQUIRED；后两种必须有依据。recommendation 具体写所需范围、格式、精度/分辨率、字段/时相或可接受替代。必需缺项只阻断依赖步骤；没有 stepIds 视为影响全链。可继续独立只读预检，不能宣称完整任务已完成。

toolChoices 每项记录 stepId、status、tools、reason、evidenceRefs。SUPPORTED/SUBSTITUTE 要实际工具发现/schema/许可/实现观测；SUBSTITUTE 另填 equivalence 和 limits。UNSUPPORTED/DEVELOPMENT_PENDING 先写 alternativesConsidered，列明现有工具组合为何不适用，再向用户提出具体开发建议。developmentConsentRef 如提供，只能引用 actor=USER 的明确开发同意记录；它不会把待开发工具变成可运行工具。已注册但未实现不算支持；已支持替代也不能偷偷改变科学方法。

同一原始任务记录经过校验后由发布器生成 workflowView；面板资料与交付页和聊天状态板共用 intake。旧记录无 intake 可以只读展示，但显示“旧记录未确认”，不能充当新任务已问询证明。有 intake 的生产/修复步骤若未确认需求、资料、成果目录，或相关必需资料未核实，或没有可执行工具方案，发布器拒绝进入 RUNNING/PRODUCED/VERIFIED。

聊天给出当前执行步骤并在 Mermaid 高亮；原生面板对 RUNNING 行显示独立绿色底色、左条及“▶ 当前步骤”文字，选中其它行不会清除。全部真实并发步骤均可高亮，无运行观测时明确无当前执行步骤。资料页列实际产物的完整路径和状态；结束时聊天逐件回报，不能只给文件夹而遗漏成果成员。面板是只读，不在本窗口收集回答；用户在对话中答复，由 Agent 更新同一记录。

新模板采用schema1.3，intake为必填对象；无intake的旧schema1.2只保留兼容展示和未确认提示。该合同覆盖PROCESS/CHECK/RECHECK/REPAIR的实际进入执行及已核验状态，不能通过删除字段绕过新记录的资料确认。0.7.0技能目录共19文件，三份交付逐件一致。
